## 1. Purpose

Re-evaluate hot-adapter feasibility after external repositories were provided for **Shard** (krish1905/shard) and **SpectralQuant** (Dynamis-Labs/spectralquant), and decide whether Phase 5b should remain SnapKV or switch priority.

## 2. Why addendum was needed

Exp 032 originally classified **ShardKV** as C (no-go) because no LLM compression repo with that name was in scope — it referred to MIT 6.824-style distributed shardkv. The user-provided **Shard** repo is a real Llama KV-cache compression system. **SpectralQuant** was not in the original candidate table.

## 3. External repositories inspected

| Repository | URL | Role |
|---|---|---|
| **Shard** | https://github.com/krish1905/shard | Llama `Cache` subclass + fused attention |
| **SpectralQuant** | https://github.com/Dynamis-Labs/spectralquant | Calibration + tensor KV compressor |

Inspection method: shallow `git clone` + README and `src/` module review (2026-06-12). No ExactKV integration run.

## 4. Shard summary

- **Real LLM KV-cache compression:** yes
- **`transformers.Cache` subclass:** yes (`shard.Cache`)
- **Llama-specific:** yes — `enable_llama_fused_attention()` patches `LlamaAttention`
- **Compressed attention without FP16 K materialization:** yes (fused int4 PCA path)
- **Monkey-patches attention:** yes
- **Triton kernels:** yes, with CPU/PyTorch fallbacks
- **E2E benchmark script:** yes (`benchmarks/benchmark.py`, Modal B200)
- **Memory vs throughput (external README):** ~10× compression; decode **0.4–0.5×** FP16

## 5. Shard ExactKV compatibility

Shard (krish1905/shard) is a **real** Llama-3.1 KV-cache compression system: `transformers.Cache` subclass, PCA+VQ asymmetric compression, fused Q·K on int4 coefficients without FP16 K materialization. README reports ~10× memory reduction at 8K but **0.4–0.5× decode throughput** vs FP16 (external results — not ExactKV). ExactKV can likely use it only as an **external drafter / Llama-only sidecar probe**, not as a Qwen KVCompressor backend without Llama + attention monkey-patch.


| Path | Assessment |
|---|---|
| A. direct KVCompressor backend | C — Shard Cache requires fused compressed-K attention and enable_llama_fused_attention() monkey-patch; not a tensor-only BackendAdapter over past_key_values. |
| B. external drafter | B — Draft with Shard Cache + patched LlamaAttention on an isolated model; full-KV verifier on authoritative HF cache (Exp 022 Mode B pattern). |
| C. Llama-only sidecar/probe | B — Best fit: Llama-3.1-8B-only legibility probe alongside Exp 033; not a default-registry compressor. |
| D. no-go | For direct KVCompressor without draft-model fork. |

## 6. Shard feasibility classification

**B — restricted feasibility** — best as **external drafter / Llama-only probe**, not direct `KVCompressor` on Qwen.

## 7. SpectralQuant summary

- **Real implementation:** yes — `src/spectralquant/` (9 modules)
- **Reusable engine/API:** yes — `SpectralQuantEngine`, `EigenspectralCalibrator`
- **TurboQuant dependency:** kernel engine subclasses `TurboQuantEngine`; baseline clone required for full repro
- **Calibration artifacts:** yes — per-model eigenspectral calibration (~15s cited)
- **Arbitrary HF `past_key_values`:** no — per-layer K/V tensor API
- **Scripts vs library:** both — 21 experiment scripts + importable library

## 8. SpectralQuant ExactKV compatibility

SpectralQuant is a **real library** (`src/spectralquant/`) with calibration, spectral rotation, non-uniform Lloyd-Max quantization, and selective QJL. It **subclasses TurboQuant** for the kernel engine and requires a `baseline/turboquant_cutile` clone for full reproduction. It operates on **per-layer K/V tensors**, not arbitrary HF `past_key_values` drop-in. Paper/repo headline metrics are **external** — not ExactKV results. Feasible as **offline calibration + tensor compressor** BackendAdapter (B).


| Path | Assessment |
|---|---|
| A. direct KVCompressor backend | B — Wrap `spectralquant.SpectralQuantEngine.compress_keys/decompress_*` in BackendAdapter after calibrating per model; materialize dequantized K/V for draft forwards. |
| B. offline calibration + tensor compressor | B — Best fit: EigenspectralCalibrator + per-layer engine; mirrors TurboQuant Python adapter (Exp 008) pattern. |
| D. no-go | If turboquant_cutile baseline cannot be installed for kernel path. |

## 9. SpectralQuant feasibility classification

**B — restricted feasibility** — **offline calibration + tensor compressor** BackendAdapter (similar to TurboQuant Python path, Exp 008).

## 11. Recommended Phase 5b path

**Primary:** `snapkv_experimental_adapter` — SnapKV experimental remains the lowest-risk ExactKV integration on Qwen (kvpress replay precedent, Exp 005).

**Shard does not preempt SnapKV for Phase 5b** — Llama-only, attention monkey-patch, external-drafter shape. Recommend **Shard Llama external-drafter probe** as optional parallel work with **Phase 6 (Exp 033 Llama-3.1-8B)**.

**SpectralQuant** deferred to **Phase 5c** (optional) — higher setup cost (calibration + TurboQuant baseline), lower name legibility than SnapKV/Shard.

| SnapKV still recommended for 5b | **True** |
| Shard/SpectralQuant preempt SnapKV | **False** |

## 12. What this proves

- **Shard** is a legitimate hot-adapter *name* for launch legibility — but integrates as external drafter / Llama probe, not Qwen KVCompressor.
- **SpectralQuant** is a real compressor library — feasible as calibrated tensor adapter.
- **SnapKV Phase 5b** remains the correct first implementation on current ExactKV stack.

## 13. What this does not prove

- Shard or SpectralQuant preserve exactness in ExactKV (not tested).
- External compression/throughput numbers transfer to ExactKV.
- Active GPU memory or speed improvements for ExactKV (Exp 031/030).

## 14. Overclaim risks

- Calling Shard integrated without isolated draft model + full-KV verifier split.
- Citing SpectralQuant paper JSON as ExactKV experiment results.
- Implying Shard decode throughput wins when README states **below FP16**.
- Registering any candidate in default compressor registry.
